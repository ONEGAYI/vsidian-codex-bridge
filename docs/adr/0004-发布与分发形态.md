# ADR-0004：发布与分发形态——渠道 / 版本兼容策略 / CI / 示例与文档

- 状态：**已按推荐先行实施，待用户追认**（票 #4 `pending-decision`，2026-10-16）
- 背景：仓库规划期即定发布形态，避免能力票（#2 粘贴还原 / #3 Mermaid Codex 主题）实施后返工——产物结构、清单字段、兼容声明都与分发渠道相关。票面待决策四项：分发渠道、版本与兼容策略、CI 流水线、示例与文档。
- 关联：[ADR-0001](0001-脚手架构建与vendor快照.md)（构建桥与 vendor 快照）、[ADR-0003](0003-mermaid-codex主题迁移.md)（Mermaid 运行时自带打包——VSIX 体积红线的基线来源）；上游 vsidian ADR-0012（分发与 API 治理，事实源在主仓库）。

## 决策一：分发渠道——首期 GitHub Release VSIX，Marketplace 留作后续可选

**采纳**：VSIX 产物（`npm run package` 产出）经 GitHub Release 分发——用户侧载安装（`code --install-extension` 或扩展面板「从 VSIX 安装」）。VSCode Marketplace **不作为首期渠道**。

**理由**：

1. **上游 API 处候选期**：vsidian 附加组件 API 1.0.0 在发行台账中仍是 `candidate`（T01–T07 合入 main 但待用户整体验收，形状可能调整）。组件上 Marketplace 即对外承诺兼容性，候选期 API 一动就得发修复版，节奏被上游绑架。
2. **发行护栏**：参照仓 vsidian-easy-typing 的票面红线沿用——对外发布需「上游 API 落账发行」与「用户明确授权」二者齐备。GitHub Release 形态下每次发布都是显式人工动作；`scripts/release.mjs` 无任何上传路径（显式拒绝 `--upload`/`--publish`），是该边界的代码化。
3. **组件本身依赖宿主先行**：`extensionDependencies: ["onegayi.vsidian"]` 决定了用户必先装 vsidian；vsidian 本体若同样走 GitHub Release，组件上 Marketplace 并不带来发现性收益。

**上 Marketplace 的触发条件**（后续可选，不设时间表）：上游附加组件 API 落账 `released` 且组件经真实使用稳定；届时补 publisher 打包校验与 CHANGELOG 机制，发布动作仍需用户授权。

## 决策二：版本与兼容——0.1.0 起步，vendor 锚 + api 范围双声明，升级走显式 re-vendor

**采纳**：

- `package.json` version 起步 **`0.1.0`**（0.x 语义：候选期组件，Minor 即破坏性变更窗口）。
- 兼容声明 = **vendor 类型快照锚 `301d2c16`**（`scripts/vendorSdkTypes.mjs` 的 `DEFAULT_COMMIT`）+ **`vsidianAddon.api: "^1.0.0"`****（现状不动）**。前者钉编译期类型面，后者是运行期宿主兼容判定入口（宿主 stable 1.0.0 必须落在本范围内才判兼容）。首期零 `experimental` 入口（ADR-0001）。
- **升级联动**：跟随上游 API 演进 = 显式三步——re-vendor（改 `DEFAULT_COMMIT` 后 `npm run vendor:sdk`）、全量回归（`npm test` + 浏览器冒烟 + 真宿主验证）、版本号 bump（人工编辑 `package.json`，联动清单见 README「安装与升级」）。**不做自动 chasing main**：锚定点跟随平台最近可用构建，不追未经验收的 main 头部。
- 组件版本号与上游 API 版本**不做公式化联动**（如「API 1.1 → 组件 0.2」）：API 台账尚在候选期，公式会把候选期抖动传导进组件版本历史；以 ADR 与 README 兼容表人工维护对应关系。

**版本发布流程无脚本化**：本仓无 CHANGELOG 机制，`scripts/release.mjs` 只做 `package` 子命令（打包 + 红线检查 + manifest 冒烟）。版本 bump 与 Release 说明是人工步骤——首期从简，上 Marketplace 时再评估引入 CHANGELOG 与 release 子命令（对齐 easy-typing 的 `promoteUnreleased` 机制）。

## 决策三：CI——单 job 串行五链路，vendor:check 以 partial clone 源仓防漂移

**采纳**：GitHub Actions（`.github/workflows/ci.yml`），push(main) / PR / 手动触发，步骤链：

```
npm ci → npm run compile → npm test → git clone --filter=blob:none ONEGAYI/vsidian
       → npm run vendor:check（VSIDIAN_SOURCE_REPO 指向克隆）→ npx vsce package → artifact 上传
```

- **形态对齐参照仓** easy-typing ci.yml（源头 vsidian 主仓）：node 22 + setup-node@v5 + cache npm；concurrency 按 ref 分组取消旧跑；测试 JSON 报告失败时上传留证（attempt 号防 rerun 覆盖）。
- **vendor:check 的源仓获取**：CI 无本地源仓路径，先 `git clone --filter=blob:none`（commit/tree 随 clone 到场，blob 由 `git show` 按需取——快照闭包仅几十个文件），再以 `VSIDIAN_SOURCE_REPO` 指向；**锚定 commit 不可达必须失败而非降级**（fail-closed——防漂移检查的意义就在与源对比）。
- **@vscode/vsce 钉精确版本**（`4.0.0`）进 devDependencies，CI 与本地 `npm run package` 同源同版本，不受 npx 浮动下载影响。
- **浏览器冒烟不进 CI**：`test/browser/smoke-mermaid.mjs` 借 vsidian 主仓 node_modules 的 Playwright 与其浏览器缓存（跨仓布局依赖），CI 上不可移植；保留本地跑法（README「开发」）。**真宿主验证（`npm run test:host`）不进 CI**：需要本地 vsidian 源仓构建产物与 VSCode 1.82.3 下载，且断言面依赖 `_test.*` 测试钩子（生产会话不注册）。两者均为「本地验证 + 日志留证」口径，CI 覆盖单元契约与打包链。
- **VSIX 体积红线归 `npm run package`**（scripts/release.mjs），CI 只构建与上传——红线检查需要解包断言，留在发布动作里比每次 push 都跑更贴近语义（对齐 easy-typing #23/#24 分工）。

### VSIX 内容红线（体积与清单依据）

`scripts/release.mjs` 的 `inspectVsixEntries` 纯函数由 `test/release.test.ts`（21 用例）钉住：

- **必需产物**：`dist/extension.js` + `dist/editor.js` + `dist/mermaid.js` + `dist/mermaid-chunks/`（**非空**——零分块即 splitting 失效或构建前清理后未重建，运行时按需加载必然 404）+ manifest/readme/license。
- **体积红线**（解压口径，2026-10-16 实测基线：84 文件 / 3.98 MB / VSIX 压缩 1.22 MB，其中 76 个 mermaid 分块 3.93 MB、最大 ELK render 块 1.4 MB——分块大头是 ADR-0003 决策一「运行时自带打包、版本对齐上游」的既定成本）：总量警告线 8 MB（约一倍余量容纳版本线升级）/ 失败线 16 MB（拦截「双大头」——mermaid 意外内联进 editor.js 或误引第二份运行时）；单文件警告线 3 MB / 失败线 6 MB。红线语义是「防意外塞进大文件/依赖」而非精确预算。
- **禁止模式 + 白名单双保险**：`.vscodeignore` 挡打包输入（源码/测试/vendor 快照/工程设施/node_modules/sourcemap/lockfile），检查器挡最终产物——未知顶层条目（工具残留）与 `dist/` 未登记产物一律拒绝，`mermaid-chunks/` 前缀放行（散列随构建变化）。
- **manifest 冒烟**：VSIX 内 `extension/package.json` 与仓库清单核对——version（打包时漂移）/ main / `extensionDependencies` / `vsidianAddon`（宿主发现机制入口）逐字段一致。

## 决策四：示例与文档——README 安装升级节从简，不建示例工程

**采纳**：README 增补「安装与升级」一节——VSIX 侧载步骤、版本兼容表（组件版本 × vendor 锚 × API 声明）、升级与降级说明（停用/卸载后宿主回落内置转换与 default 主题，降级底线）。**不另建独立示例工程**：本组件自身就是「粘贴规则 + 主题 + 渲染提供者」的完整接入样例，上游 `test/examples/`（T15 三套样例）与 developer-guide 已承担教学职能；票面的独立示例仓库方向记为**后续可选项**（有外部插件作者诉求时再议）。

## 真宿主安装验证（衔接票 #3 遗留项）——静默宿主基建（常驻）

**通道形态**：`npm run test:host -- --host <vsidian仓根>`（`test/host/` 常驻基建层，与 vitest 单元层、浏览器冒烟层并列）。宿主验证起真实 VSCode **1.82.3**（engines 下界）实例——**必须经静默通道**，禁止在用户当前桌面出现任何 GUI 进程：

- `test/host/hiddenDesktop.ps1`：自同作者上游仓 ONEGAYI/vsidian **原样复制**（`test/integration/hiddenDesktop.ps1@301d2c16`，244 行，仅加来源头注）。机制：Win32 API 创建**独立窗口站 + 独立桌面**，`CreateProcess` 的 `lpDesktop` 指向它，宿主窗口对用户桌面不可见、剪贴板随窗口站隔离；`CREATE_SUSPENDED` → Job Object（`KILL_ON_JOB_CLOSE`）→ `ResumeThread`，启动器退出即清理整个进程树。结束时输出**静默性证据行**：「测试桌面可见窗口峰值 N；观察期间前台 PID …；结束时前台 PID …」。
- `test/host/silentHost.mjs`：启动包装（上游 `testHost.mjs@301d2c16` 的 spawn 包装节选适配——报告落盘、超时/信号收尾、尾行缓冲原样；未迁移上游专有的便携分片/集成报告判定函数）。Windows 经 `powershell -NonInteractive -File hiddenDesktop.ps1`（Base64 配置、`windowsHide`）；**非 Windows 拒绝运行**（PR #5 约定统一）：无隔离后端时静默回落 foreground 会在用户桌面弹出宿主 GUI，违反「宿主层禁止用户桌面可见 GUI」约定——`resolveTestHostMode` 对缺省与显式 `foreground`/`desktop` 请求一律抛错说明原因（显式请求同样拒，无隔离后端时不存在合规的可见模式），入口 `run.mjs` 在下载 VSCode 之前预检；上游本体在 Linux CI 用 foreground 跑集成测试是其仓库的口径，本仓不继承。如未来需要 Linux/macOS 宿主层（如 CI 化），先为该平台提供隔离后端（Linux 下 xvfb/headless 方案）再放开。
- `test/host/run.mjs` + `suite.ts`：入口（套件 esbuild 构建、宿主仓定位与 batch-2 面自检——产物不含 `_test.addonThemes` 即拒跑防旧宿主假红、VSCode 缓存复用/下载、临时工作区）与宿主内四层断言。
- 基建本身由 `test/host-infra.test.ts`（6 用例）钉住：文件在场、npm 入口、ps1 来源指向与静默关键 API（CreateWindowStation/CreateDesktop/lpDesktop/KILL_ON_JOB_CLOSE/证据行）未被误改、`npm test` 不级联宿主层。

**与 `npm test` 的关系**：独立入口不级联——宿主验证依赖外部 vsidian 仓构建产物与 VSCode 1.82.3（缓存缺失时约 130 MB 下载），级联会破坏单元层「秒级、零外部依赖」的属性。本仓后续一切宿主层验证（含 #3 衔接项、未来回归）默认走本通道。

**四层断言**（观测全部经 vsidian `_test.*` 测试钩子，`VSIDIAN_TEST_HOOKS=1` 会话注册）：① 组件激活无错（isActive，extensionDependencies 联动 + registerAddon 成功）② 主题目录出现 Codex 候选且 available（设置「外观→主题」数据源）③ 选择后 mermaid 容器 provider = 本组件渲染器 + width>0 + builtinSvg=0——**webview CSP 下 esm 分块真实装载的端到端证明**（ADR-0003 未尽项闭环）④ 停用回落内置 builtin 且主题首选保留（降级底线）。断言链含设置落地显式前置等待（`setSettings` 广播是异步的，不等待会窗口竞态）。

**验证历史与边界**：

- 2026-10-16 首轮自动化运行（当时未接静默通道，宿主窗口出现在用户桌面，被叫停）**四层断言已全部通过**（证据：`release-logs/host-check-evidence.log`：激活 109ms / 候选在场 / 渲染 537ms width=624 / 停用回落 689ms）；随即按用户指示接入上游静默机制，后续运行一律走独立桌面。
- 暗色填充与私有全局名在宿主侧无程序化观测面（平台 paint 探针 color 对 SVG 叶子恒透明、webview 全局不可从扩展宿主读取）——色板逐值证据由浏览器层冒烟承载（ADR-0003），两处人工证据点（暗色 `#181818` 填充、Webview Developer Tools 中 `__vsidianCodexMermaid`）收录于 README 手动验证清单，作为用户验收参考（非唯一通道）。
- VSIX 安装态装载（`--install-extension`）与开发装载（development path）在 `extensionDependencies` 解析路径上有差异，安装态验证以 README 手动清单承载（清单第 1–2 步即侧载安装态）；上游 #535（内核退役）联动验收时如需安装态自动化回归，复用本通道扩展 `--install-extension` 前置即可。

## 已知边界与未尽事项

- **CI 未真跑**：本地无 Actions 运行时；首次 push 后以实际运行为准。工作流与 easy-typing（已投产同款）逐行同构，结构性风险低。
- **宿主手动验证清单为验收参考**（非唯一通道）：自动化覆盖激活/候选/选路/回落四层；暗色填充与私有全局名两处人工证据点及用户真实环境验收走 README「宿主安装手动验证」清单。
- **发布动作本身不执行**：本票只交付脚本/工作流/文档与本地验证；GitHub Release 的创建时机与内容待用户决策。
